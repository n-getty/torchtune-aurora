# Kimi-K3 serving — handoff, 2026-08-10

Read this first, then `STATUS_20260810.md` for the full result tables.
Everything below is committed; both git trees are clean.

---

## 1. Where we are in one paragraph

K3 achieved **65.20 output tok/s** on 3 nodes (TP=32, EP-on, c=128), sustained
33.5 minutes, 256/256 requests, correctness-gated — **10.05x** the previous
best of 6.489 and the first number in the same order as the Qwen3-Coder-480B
reference (106.19). But that result only reproduces at
`max_num_batched_tokens=2048`, which is too small for real serving. Above that
the engine dies with `banned:1` after 2-6 requests. The leading hypothesis —
**not yet tested** — is that this is the same L0 handle-table exhaustion class
already documented twice in `docs/bugs/`, not a GPU OOM.

## 3. THE OPEN BLOCKER — and the strongest lead

### The discriminator is `max_num_batched_tokens`

Grouping all 11 servers from the session by `mnbt` separates perfectly:

| `mnbt` | healthy | faulted | notes |
|---|---|---|---|
| **2048** | **4 / 4** | 0 | includes `max_num_seqs=384`, 1200 blocks |
| 4096 | 0 | 6 | across **four different allocations** |
| 8192 | 0 | 1 | on the **known-good** x4315 nodes |

Not confounded with node set (4096 failed everywhere; 8192 failed on the good
nodes). Not confounded with `max_num_seqs` (384 was healthy at 2048; 128 failed
at 4096). Not memory pressure (util 0.92 + 1200 blocks healthy; util 0.84 + 700
blocks faulted).

Failures are **request-count-bounded, not time-bounded**: 2-6 completed
requests, usually seconds in. The healthy server ran ~57 minutes.

### Why this is probably NOT a GPU OOM

`banned:1` / `UR_RESULT_ERROR_OUT_OF_RESOURCES` (L0 error 40) is signature #3
in our own `docs/bugs/UPSTREAM_FILING_DRAFT_l0_resource_pool.md`. This codebase
has hit the same class **twice**, both times from transient per-call
allocations, and both times at low memory:

- `memory/project_qwen3_moe_padded_bmm_l0_exhaustion_fix_20260721.md` —
  `GroupedExpertsHF.forward()` did `x.new_zeros(E, max_count, dim)` on every
  call; crashed at **19-41 GiB of a 64 GiB tile**. The trigger was proven to be
  the **chunk shape**, not total memory: a run at *half* the memory crashed
  identically. Fixed by `TORCHTUNE_MOE_SEQUENTIAL_EXPERTS=1`.
- `memory/project_expert_forward_fix.md` — the same thing 100 days earlier in a
  different MoE model.

**vLLM's XPU MoE path has the same shape.** `xpu_moe.py:164` returns
`workspace1 = workspace2 = (0,)` — i.e. it pre-allocates *nothing* — and the
kernel then allocates per call. In
`wheel_patches/vllm_xpu_kernels_0.1.7_fused_moe_interface.py` there are **7
fresh `torch.empty`/`torch.zeros` per MoE invocation** (lines 189, 201, 213,
217, 220, 255, 282), several sized by `num_moe_inputs = tokens x topk`.

For K3 (92 MoE layers, topk=16) that is ~644 transient allocations per step,
and `mnbt` scales each one:

| `mnbt` | `num_moe_inputs` | allocs/step |
|---|---|---|
| 2048 | 32,768 | ~644 |
| 4096 | 65,536 | ~644 |
| 8192 | 131,072 | ~644 |

The *count* is constant; the *size* doubles. That fits a VA-range/handle
pressure story and fits the padded-BMM precedent. **It is a hypothesis, not a
finding — nobody has tested it.**

### Why `mnbt=2048` is not an acceptable answer

`max_num_batched_tokens` caps tokens processed per scheduler step. At 2048, a
single 4096-token prompt cannot be admitted in one step. K3 advertises up to 1M
context. So the honest status is: **we have a working config only in a regime
too narrow to serve real traffic.** This is the thing to fix.

## 4. Recommended next steps, cheapest first

1. **A/B `mnbt` on ONE allocation** (3 nodes, ~40 min). Two servers, 2048 vs
   4096, everything else byte-identical, same nodes. This is the experiment
   that settles §3 and it has never been run — every prior comparison changed
   nodes too. *Do this before any code work.*
2. **Read `vllm_xpu_kernels`' fused MoE for a preallocation path** (free). If
   the 7 per-call buffers can be hoisted into `workspace_shapes` (which
   currently returns zero-sized workspaces), that is the direct analogue of the
   `SEQUENTIAL_EXPERTS` fix and would lift the `mnbt` ceiling.
3. **48B surrogate with EP-on** (FREE debug queue, ~10 min). The 48B has
   `num_experts: 256`. If EP-on + high `mnbt` reproduces `banned:1` on one
   node, there is a 10-minute reproducer instead of a 3-node hunt. An attempt
   was lost to the cache gotcha in §7.
4. **Then** re-measure: `max_num_seqs=384` at `mnbt=2048` was healthy and never
   benchmarked. Fitting the two real points gives
   `step(c) = 1.249 + 0.00516c` -> ~100 tok/s at c=256, ~119 at c=384.

## 5. Other findings worth keeping

**KV pool starvation (25x), fixed by workaround.** 11 of 32 ranks — every one
an *odd* local tile, i.e. the second tile of a shared physical card — profile
~0.34 GiB free instead of ~8.5 GiB, because `mem_get_info` is device-wide and
an odd tile profiling concurrently with its even sibling absorbs the sibling's
allocation. vLLM clamps `num_blocks` to the min across ranks, so one bad
reading shrank the pool from 1722 blocks to 69. Confirmed an artifact: once
loaded every tile reports a uniform ~13.8 GiB free. Real fix would be to
serialize sibling-tile profiling or treat `available_memory` as per-card;
`--kv-cache-memory-bytes` is a cleaner workaround than `--diagnostic-blocks`
because it skips profiling entirely.

**Prefill is the next bottleneck after the fault.** `kda.py`'s "vectorized"
prefill batches across sequences but steps **one token at a time**, so a
1024-token prompt is ~70,656 sequential einsum groups per layer pass. A K3 c=1
cell at 256-in did not finish one request in 18 min; a 48B cell at 512-in x
c=32 died of `execute_model` RPC timeout (not `banned:1`).
`prototype_chunked_delta_rule.py` has a **CPU-validated fix** (4 shapes, max
error ~1e-7): with `A_t = exp(cumsum(g)_t)` and `S_t = Shat_t * A_t` the
recurrence becomes a unit lower-triangular solve per chunk. **C=16 is forced by
numerics, not tuning** — K3 clamps `g >= -5` so a C-token chunk reaches
exponent 5C against fp32's ~88 limit (C=32 overflows). At C=16 a 1024-token
prefill drops from 1024 iterations to 64. Not yet wired into `kda.py`.

**Multi-node DP is structurally impossible for K3.** vLLM asserts
`world_size(TP) % devices_per_node == 0` **in the DP placement path only**
(`vllm/v1/engine/utils.py:526-539`) -> `TP % 12 == 0`, while K3 needs
`163840 % TP == 0`. No TP satisfies both. **Note plain TP=32 is unaffected** —
that assertion is never reached without `--data-parallel-size > 1`, which is
why the 65.20 run worked at `32 % 12 = 8`. Scale-out therefore needs N
independent TP=32 servers behind a load balancer (9 nodes), not vLLM DP.

**Aggregate vs per-user.** K3 at c=128: 65.20 aggregate but ~0.52 tok/s per
user — a batch engine, not an interactive one. The 48B surrogate (TP=2, 1 node)
shows what healthy scaling looks like: c=1 -> 8.86 agg / 8.87 per-user;
c=32 -> 218.8 agg / 6.86 per-user. Aggregate scales ~25x while per-user
degrades only ~23%.

**48B surrogate is clean** on the same driver/frameworks/node-pool/vLLM tree —
correctness 4/4, concurrency ladder c=1..32 with zero failures. That ruled out
cluster/driver/hardware as the cause of `banned:1`. It ran at `mnbt=2048`,
which in hindsight is consistent with §3 and means it has **not** yet tested
the high-`mnbt` regime.

## 6. Hypotheses already eliminated — do not re-test

1. Bad hardware (generic) — nodes passed a per-tile health check (62.3 GiB free
   on all 12) minutes before faulting.
2. `--no-enable-chunked-prefill` — chunked-ON died identically elsewhere.
3. Retry-in-place leaking 5-9 GiB/tile — a first start on clean nodes faulted.
   (The leak is real; still worth avoiding.)
4. `max_num_seqs >= 192` — **RETRACTED**; c=128 faulted and 384 was healthy.
5. The `merge_attn_states` torch fallback (commit `6c9d079a`) — refuted by
   reverting it.
6. **Any repo code state** — refuted decisively: checked out the exact
   successful commit `781b27d2` with a provably clean tree (`VLLM_DIFF_SHA256`
   = sha256 of empty diff), identical 117,028-token KV pool, faulted after 6
   requests. **Caveat: that run used `mnbt=4096`, so it was not a full control
   after all** — which is how the `mnbt` correlation was finally spotted.
7. Cluster/driver-wide — refuted by the clean 48B run.

## 7. Operational gotchas

- `serve_k3.sh` **refuses to start if `K3_CACHE_ROOT` already exists and writes
  NOTHING to `launcher.log`**. A zero-byte log means this, not a slow start.
  Use a distinct cache root per launch.
- `vllm bench serve` needs its **own** `--trust-remote-code` (it loads the
  tokenizer in the client process) **and** the model dir on `PYTHONPATH` (K3's
  remote-code tokenizer imports a sibling `encoding_k3.py` that
  `transformers.check_imports` resolves against the client's `sys.path`).
- `vllm bench serve` applies one `PROMPTS` value to every concurrency cell, so
  its 128-prompt default is 128 *sequential* generations at c=1 (~19 h). Use
  `run_concurrency_ladder.sh` or `probe_concurrency_direct.py`.
- `vllm bench serve` returned HTTP 503 for every request against the 48B while
  plain `/v1/completions` POSTs succeeded — its failures are not evidence about
  the server. `probe_concurrency_direct.py` bypasses it.
- A failed vLLM start leaves 5-9 GiB/tile allocated with **no process holding
  it**. Don't retry in place; get fresh nodes or accept less memory.
- SSH to compute nodes hung for several minutes at one point (login-node load
  14, PALS `mpiexec` also failing). It cleared on its own — not an allocation
  problem.

## 9. A process warning for the next agent

Several conclusions this session were published and then retracted: the "34x KV
inflation" mechanism, the `max_num_seqs >= 192` ceiling, and two successive
attributions of `banned:1`. The recurring error was **reporting a correlation
before running the experiment that would falsify it**, and **changing several
variables between runs** so that comparisons weren't controls. The `mnbt`
discriminator was visible in every launch command from the start and was missed
because it was never put in a column.

Concretely: before concluding anything from a K3 run, diff its
`server/effective_environment.txt` and the launch line against the known-good
config above. If more than one variable differs, it is not a control.
