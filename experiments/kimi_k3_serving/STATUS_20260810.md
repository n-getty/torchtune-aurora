# Kimi-K3 serving — status as of 2026-08-10

## Headline

**65.20 output tok/s on 3 nodes (TP=32, EP-on), sustained for 33.5 minutes,
256/256 requests successful, correctness-gated.** That is **10.05x** the
previous best of 6.489 tok/s and the first K3 result in the same order of
magnitude as the Qwen3-Coder-480B reference (106.19 tok/s on the same machine).

Config: `--max-num-seqs 128 --max-num-batched-tokens 4096
--gpu-memory-utilization 0.92 --diagnostic-blocks 800 --max-model-len 2048
--ep --no-async-scheduling`, both Triton flags OFF, both VECTORIZED flags ON.
Benchmark: `vllm bench serve`, 256 prompts, 32-in / 512-out, `--ignore-eos`,
`--max-concurrency 128`. Log: `logs/k3_hc_8746183/highconc_c128.log`.

## What it took to get there

Three blockers, all previously invisible:

1. **KV pool starvation (25x).** 11 of 32 ranks — every one an *odd* local
   tile, i.e. the second tile of a shared physical card — profile ~0.34 GiB
   free instead of ~8.5 GiB, because `mem_get_info` is device-wide and an odd
   tile profiling concurrently with its even sibling absorbs the sibling's
   allocation. vLLM clamps `num_blocks` to the minimum across ranks, so one
   bad reading shrank the pool from 1722 blocks to 69. Confirmed an artifact:
   once loaded, every tile reports a uniform ~13.8 GiB free. Bypassed with
   `--diagnostic-blocks`; without it 128 concurrent sequences do not fit at all.
2. **`vllm bench serve` needs its own `--trust-remote-code`.** It loads K3's
   tokenizer in the *client* process to build the random dataset.
3. **The bench client needs the model dir on `PYTHONPATH`.** K3's remote-code
   tokenizer imports a sibling `encoding_k3.py`, and `transformers.check_imports`
   resolves that against the client's `sys.path`, not the model dir.

## Aggregate throughput vs single-user latency

These diverge sharply and a single headline number misleads.

**K3, 3 nodes, 32-in/512-out:**

| concurrency | aggregate tok/s | per-user tok/s | mean TPOT |
|---|---|---|---|
| 8 | 6.489 | ~0.8 | — |
| 128 | **65.20** | **~0.52** | 1909 ms |

At peak aggregate a single user sees about half a token per second. K3 at this
configuration is a batch-throughput engine, not an interactive one.

**48B Kimi-Linear surrogate (TP=2, 1 node, 32-in/64-out)** — measured as a
control, and the first clean scaling curve on this hardware:

| concurrency | aggregate tok/s | per-user tok/s | mean latency |
|---|---|---|---|
| 1 | 8.863 | 8.866 | 7.22 s |
| 4 | 32.502 | 8.187 | 7.86 s |
| 16 | 119.957 | 7.51 | 8.52 s |
| 32 | **218.785** | 6.863 | 9.35 s |

Aggregate scales ~25x from c=1 to c=32 while per-user degrades only ~23%.
K3's tradeoff is far worse than this, which is itself a clue.

## Open blocker: `banned:1` on non-x4315 node sets

Grouped by **node set** rather than by config, the pattern is stark:

| node set | servers | completions | `banned:1` |
|---|---|---|---|
| x4315c5s1/s2/s4 (job 8746183) | 5 | 332 + 390 + 774 + 393 + 6 | 0, 0, 0, 0, **98** |
| 8746327 / 8746385 / 8746446 / 8746405 | 6 | 0–6 each | all faulted |

**4 of 5 servers on x4315 were healthy — 1,889 completions with zero faults.
0 of 6 servers on every other node set were healthy.** The single x4315 fault
is the one run using `CHUNKED_PREFILL=0`, a workaround I had added and have
since reverted.

The failures are **request-count-bounded, not time-bounded**: they die after
2–6 completed requests, usually seconds in. The healthy server ran ~57 minutes.

### Hypotheses tested and eliminated

Each was formed, published, and then disproved by direct experiment. Recorded
so they are not re-tried:

1. **Bad hardware (generic)** — nodes passed a per-tile memory health check
   (62.3 GiB free on all 12) minutes before faulting.
2. **`--no-enable-chunked-prefill`** — chunked-ON died identically on other
   node sets. (Though note it *is* the only x4315 fault; see below.)
3. **Retry-in-place leaking 5–9 GiB/tile** — a first start on clean nodes
   faulted too. The leak is real and worth avoiding, but is not the cause.
4. **`max_num_seqs >= 192`** — **RETRACTED.** c=128, the exact value that
   produced 65.20, later faulted at 3 requests.
5. **My `merge_attn_states` torch fallback** (commit `6c9d079a`, landed
   between the success and the first failure — a compelling timeline) —
   refuted by reverting it.
6. **Any repo code state at all** — refuted decisively: checked out the exact
   successful commit `781b27d2` with a provably clean tree (`VLLM_DIFF_SHA256`
   = sha256 of an empty diff, byte-matching the successful run's recorded
   pair), got the identical 117,028-token KV pool, and it faulted after 6
   requests.
7. **Cluster/driver-wide** — refuted: the 48B surrogate runs clean on the same
   driver stack, frameworks, node pool and vLLM tree.

### Where that leaves it

The fault is **K3-specific and node-set-correlated**. Two readings remain, and
they are not yet separated:

* **Node-set health.** All healthy runs came from one allocation. PBS assigns
  semi-randomly, so this could be a genuinely better set of cards, or a
  coincidence of n=1 allocation.
* **A latent K3 config fragility** that most allocations trip and x4315 did
  not.

Cheapest next steps, all free on the `debug` queue:
* 48B with **EP-on** (`num_experts: 256`) — the largest config difference from
  K3 and the top suspect. An attempt was lost to a launch failure (below).
* 48B across **2 nodes** — separates multi-node from EP.
* Request an **x4315-rack allocation explicitly** and re-run the 65.20 config.

**Launch gotcha:** `serve_k3.sh` refuses to start if `K3_CACHE_ROOT` already
exists and writes *nothing* to `launcher.log` when it bails — a zero-byte log
means this, not a slow start. Use a distinct cache root per launch.

## 8-node scale-out: structurally impossible with vLLM DP

```
vLLM multi-node DP:  world_size (TP) % devices_per_node == 0  ->  TP % 12 == 0
Kimi-K3 vocab shard: vocab_size % TP == 0                     ->  163840 % TP == 0
```

No TP satisfies both. TP=32 fails the first; 12/24/36/48/60/72/84/96 all fail
the second (163840 = 2^12 x 40 is never a multiple of 12). The assertion is
`For multi-node data parallel groups, world_size (32) must be a multiple of
number of devices per node`.

**Four genuine multi-node DP bugs were found and fixed before hitting that
wall.** All committed and independently useful; each presented as a silent hang:

1. `ray_executor_v2` built the torch.distributed TCPStore from Ray's
   `node_ip`, which Aurora reports as `127.0.0.1` (vllm-xpu-src `37e1feab`).
2. The DP coordinator used `data_parallel_master_ip`, also loopback, because
   the default `mp` backend never calls `get_ip()` — needs
   `--data-parallel-backend ray`.
3. `RAY_ADDRESS` was computed but never exported, so the DP coordinator's bare
   `ray.init()` started its own **single-node** Ray instead of joining the
   8-node cluster.
4. `VLLM_RAY_DP_PACK_STRATEGY=strict` (the default) demands every replica fit
   on the 12-tile master node; `span` is required. Also the v1 Ray path's
   `require_gpu_on_driver=True` rejects any DP layout on a fully-subscribed
   allocation, so `--ray-v2` is mandatory.

The remaining route to 8-node scale-out is **N independent TP=32 servers behind
a client-side load balancer** (3 servers x 3 nodes = 9 nodes), not vLLM DP.

## Long prompts: prefill is the next real bottleneck

`kda.py`'s "vectorized" prefill batches across sequences but still steps **one
token at a time**, so a 1024-token prompt is ~70,656 sequential einsum groups
per layer pass. Consequences observed:

* A K3 c=1 cell at 256-in did not complete one request in 18 minutes.
* A 48B cell at 512-in x c=32 killed the server with
  `TimeoutError: RPC call to execute_model timed out` — **not** `banned:1`.

**A fix is derived and CPU-validated** (`prototype_chunked_delta_rule.py`).
With `A_t = exp(cumsum(g)_t)` and `S_t = Shat_t * A_t` the recurrence becomes a
unit lower-triangular system in the value-deltas, solved once per chunk:

```
u = w - M u,   M[t,i] = beta_i <k_i/A_i, A_t k_t>   (i < t)
o_t = Shat_0 @ (A_t q_t) + sum_{i<=t} beta_i u_i <k_i/A_i, A_t q_t>
```

Validated against the per-token loop over 4 shapes including a
non-multiple-of-chunk length: max |dout| ~1e-7, max |dstate| ~2e-6.

**Chunk size is bounded by numerics, not tuning:** `1/A_t = exp(-cumsum g)` and
K3 clamps `g >= gate_lower_bound = -5.0`, so a chunk of C tokens reaches
exponent 5C against fp32's ~88 limit. **C=16 is safe (80); C=32 overflows
(160).** At C=16 a 1024-token prefill drops from 1024 iterations to 64.

Prototype only — not yet wired into `kda.py`, not yet run on XPU.

## Not obtained

* **K3 realistic-load characterization** (256- and 1024-token prompts). The
  suite is written, committed and validated (`bench_full_characterization.sh`);
  every server since ~02:00 failed its correctness gate before any throughput
  cell ran. The gate did its job.
* **K3 single-user (c=1) baseline.** Only the c=128 datapoint exists.
* **>100 tok/s.** Fitting the two real K3 points gives
  `step(c) = 1.249 + 0.00516c`, projecting ~100 tok/s at c=256 and ~119 at
  c=384 — i.e. reachable by concurrency alone *if* a healthy server can be
  obtained. Scaling is sublinear, not fixed-cost as originally assumed.

## Tooling added this session

| file | purpose |
|---|---|
| `probe_concurrency_direct.py` | Raw-HTTP concurrency ladder reporting **both** aggregate and per-user tok/s. Needed because `vllm bench serve` returns HTTP 503 against the 48B while plain POSTs succeed. |
| `bench_full_characterization.sh` | One server start -> peak / single-user / realistic-shape phases, correctness-gated, peak-first so an engine death still leaves the important cells on disk. |
| `launch_once.sh` | Measures worst-tile free memory, derives util and block count from it, refuses an already-consumed node set, starts exactly once. |
| `analyze_block_profile.py` | Names the rank that set the KV pool floor (vLLM clamps before the profile is written, so all ranks look identical). |
| `probe_batched_nan_logprobs.py` | Separates corrupt batched logits from a logprobs-only bug from a request-ordinal effect. |
| `prototype_chunked_delta_rule.py` | The validated chunked prefill algebra. |
| `VLLM_LOG_KV_CACHE_SPECS=1` | Per-layer KV page dump before/after both unification passes. |

## Process note

Several conclusions in this session were published and then retracted after
testing: the "34x KV inflation" mechanism, the `max_num_seqs >= 192` ceiling,
and two successive attributions of the `banned:1` fault. Each retraction is
recorded in `RESULTS.md` and `memory/`. The recurring error was reporting a
correlation before running the experiment that would falsify it — most
expensively when a compelling timeline (my own commit landing between the
success and the first failure) turned out to be coincidence.
